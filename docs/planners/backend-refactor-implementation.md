# Backend refactor and implementation plan

> The one progress file for the refactor-and-build run (PR-15 in
> [decision-log.md](../decisions/decision-log.md)). The design review
> ([DBML](../design/domain-model/domain-model.dbml) + decision log) is the
> owner's confirmation of scope: no per-feature planners, no stops for
> approval. Work on `master`, `make check` + commit + push after every step.
> Client flows: [mobile app](../scenario/mobile-app.md),
> [web portal](../scenario/web-portal.md). Features:
> [features.yaml](../product/features/features.yaml).

## Rules in short

- Schema: one baseline migration (`0001_baseline_schema.py`), `make db-reset`,
  `make db-check`; small DBML deviations are recorded in the decision log + DBML.
- Skipped for the whole run: parked groups (support beyond `support_cases`,
  policy, subscription plans/invoices, `driver_scores`, geofence redesign,
  `promotion_campaigns`), open questions 4, 5, 7-11, every `deferred.md` item,
  features not in release P1.0, anything needing a large redesign.
- External providers (VietQR notifications, Firebase push, e-mail, OTP SMS)
  sit behind an interface with a logging fake. Command channel:
  `charging_station_commands` (PR-16).
- Tests lean: 1-2 smoke tests per feature; `make backend-test-integration`
  once per package that changes the schema or a repository.

## Open points

(Question + the assumption taken. Added as they come up.)

- **WP1 chunk 1, history without a reason**: DM-21 says a tracked change without a reason fails; services have no acting user yet. Assumption: the trigger records `Unspecified change` and a NULL actor (DM-29 in the decision log, rule in `database.md`); the fleet repository sets fixed reasons for edit/delete.
- **Chunk 1, history tables are not models**: `<singular>_history` tables are built from the live source table by `app/libs/db/history_ddl.py` and excluded from autogenerate by name; the DBML marks a built one with `@history built` (new tag, domain-model tool adapted: `check` skips generated history tables).
- **Chunk 1, enums as varchar**: the DBML types every identity status/role/purpose as `varchar(n)` with a `Values:` list and no check constraint, so the columns are plain `String` and the allowed values live in `identity/types.py` enums (no DB-level value check).
- **Chunk 1, `user_role_assignments` keys**: both the two-column FK `(membership_id, organization_id)` and the single `membership_id` / `organization_id` FKs of the DBML Refs are created; the domain-model `check` now accepts a Ref that matches any of a column's FKs.
- **Chunk 1, fleet creation takes `organization_id` in the body** (required) until WP2 adds authentication; an unknown organization is detected from the FK violation (404 `FleetOrganizationNotFoundError`) because the identity domain has no service yet.
- **Chunk 1, identity import-linter contract** lists only `identity.models` as forbidden (the other modules do not exist yet); WP2 adds `repository`/`router`/`schemas` when it creates them. Ruff's `banned-from` already lists the future `identity.service` / `identity.repository`.
- **Chunk 1, `added_by` / `removed_by`** are parameters of the fleet repository only (default `None`); the service does not pass them until the caller is known (WP2).
- **Chunk 2, batteries and warranties live in their own domains** (`backend/app/domains/batteries`, `warranties`; VH-13, VH-14) with models and enums only, not in `vehicles/models.py`; each has an import-linter contract (`models` forbidden) and a ruff `banned-from` entry. WP3 adds services, repositories and endpoints there.
- **Chunk 2, no activation**: `vehicles.activation_status`, `mark_device_assigned`, `mark_vehicle_activated` and `GET /vehicles/activation-summary` are removed (VH-06); the computed activation and success rate are for WP4 (VH-20).
- **Chunk 2, vehicle pack capacity** is the vehicle model's nominal capacity only; the installed battery's design capacity (VH-16) needs `batteries` to be readable and comes with WP3/WP4 (VH-20).
- **Chunk 2, vehicle create body**: `organization_id` and `vehicle_model_id` are required body fields, `acquired_at` is optional (default now); `/vehicle-models` create/list/get exist so a vehicle can be created. Ownership transfer (VH-12) is WP3.
- **Chunk 2, status of period views**: both `vehicle_ownership_periods` and `battery_installation_periods` are created by the baseline migration (the DBML defines both); no code reads them yet.
- **Chunk 3, status reports not ingested**: `telematic_status_reports` exists (model, migration, newest report read for the device response) but nothing writes it: the status-topic fields are provisional (mqtt-spec.md 2.2). WP4 adds the consumer once the vendor confirms the format.
- **Chunk 3, API names kept**: HTTP responses and the MQTT payload keep `soc`, `speed`, `message_uuid`, `signal_strength`...; only table columns carry the unit names (TM-16, TM-18). `GET /telemetry/.../latest` still returns `telematic_serial`, resolved from `telematic_id` through the telematics service.
- **Chunk 3, device create**: `organization_id` is a required body field (like vehicles), `acquired_at` defaults to now, `installed_at` is set to now when a device is mounted (create or update) and cleared when unmounted; a soft delete sets INACTIVE, unmounts and stores the reason (DM-25). The organization is not validated beyond the foreign key (404 from SQLSTATE 23503, like vehicles).
- **Chunk 3, config push**: the single and fleet pushes still refuse an INACTIVE / not-ACTIVE device but do not require the device to be mounted (TX-08 says only a mounted, ACTIVE device receives configuration); the organization-wide interval push (TX-09) is WP4.
- **Chunk 4, identity gets a first service**: `identity/service.py` + `repository.py` hold only `resolve_membership_person_reference` (membership + user); `identity.repository` is now in the identity import-linter contract. WP2 extends them.
- **Chunk 4, driver API shape**: `POST /drivers/` takes `membership_id` (the driver's name/phone moved to users, DR-09); the list searches the licence number only. A duplicate licence number across persons is not warned about (DR-09's warning is for the app/portal).
- **Chunk 4, check-in without authentication**: `/driving-sessions` endpoints take `driver_id` in the body; ineligible drivers get `400` (no "forbidden" error base). A driver whose open session is on the same truck gets that session back (idempotent check-in).
- **Chunk 4, session auto-end and ownership change**: `AUTO_ENDED` (needs telemetry + `organization_settings`) and `OWNER_CHANGED` (VH-12 transfer) are never written yet; the end-cause values exist.

- **Chunk 5, search is public-only**: the nearby search and the nearest-station lookup return only public, ACTIVE locations (CS-25); private-location visibility for the owner's members and granted organizations needs the caller's organization (WP2). Results stay one row per charger.
- **Chunk 5, no authentication on the new endpoints**: location creation takes `organization_id`, a grant takes `granted_by` and a command takes `requested_by` in the body (like the other chunks); an unknown organization or user shows as a conflict / input error from the foreign key.
- **Chunk 5, change reasons**: updates of tracked rows use fixed reasons (`Charging station edited`, ...) or the typed `status_reason` when a person takes something out of service; `changed_by` stays NULL until WP2 (same as DM-29).
- **Chunk 5, soft delete cascade**: deleting a location deletes its chargers, EVSEs, guns and closes its live grants (`revoke_reason` "Location left the system", `revoked_by` NULL); deleting a charger deletes its EVSEs and guns. API delete endpoints take an optional `status_reason` query parameter.
- **Chunk 5, the API still has no endpoint to read a charger's state history**: the raw log is the history (CS-15).
- **Chunk 5, command rows are queued by the API**: `POST /charging-stations/{id}/commands` returns 202 and the caller polls `GET .../commands/{command_id}`; the remote start for a QR charge is queued by `charging_sessions` in WP8 through `queue_station_command` (public in the charging_stations service). A manual REMOTE_START without a session needs `parameters.id_token`.
- **Chunk 5, 2.0.1 `CHANGE_CONFIGURATION`** addresses the component `OCPPCommCtrlr` unless `parameters.component_name` says otherwise (SetVariables needs a component; the DBML only has a key and a value).

- **Chunk 6, a start needs a scan (CE-16)**: `organization_id` and `started_by` are required, so the session service cannot accept an unknown tag any more; a start message must carry the token of a PENDING session of that charger, otherwise the adapter answers `Invalid`. `POST /charging-sessions/scan` (CE-20) issues the token. WP8 still owns: the remote start through `queue_station_command`, the wallet minimum, the truck from the driver's open driving session, the abandoned sweep, Authorize validation.
- **Chunk 6, notification read state needs a person**: the read / unread-count / mark-all endpoints take `user_id` as a query parameter until authentication (NT-13); recipients are added by the producer (`add_notification_recipients`); WP10 derives them from roles (NT-15).
- **Chunk 6, SOS needs an organization (SP-08)**: an SOS naming neither a known VIN nor an `organization_id` is refused with a 400, because its alert belongs to an organization.
- **Chunk 6, summary SoC from any location (CE-18)**: the simulator and most chargers send `SoC` without a location, which is stored as the default `Outlet`; only power and energy are read from `Outlet`.
- **Chunk 6, history tables of the new tracked tables** (`organization_notification_setting_history`, `tariff_history`, `charging_session_bill_history`, `wallet_history`) come from the shared `history_ddl` helper; `wallet_history` leaves `balance` out.
- **Chunk 6, parked DBML tables stay `@status planned`**: the domain-model tool has only built / planned / proposed, so the parked tables keep `planned` with their "review parked" notes.

- **WP2a, tokens (ID-46)**: the access token is an HMAC-signed `<session_id>.<expiry>.<signature>` checked against the session row, the refresh token an opaque random value stored hashed and rotated at each refresh, passwords use `hashlib.scrypt`; no JWT and no new dependency. `IDENTITY_TOKEN_SECRET_KEY` has no default: when empty a random key is drawn per process (tokens die at restart; fine for development, set it elsewhere).
- **WP2a, status codes (ID-47)**: 401 wrong credentials / bad token, 403 locked account, inactive organization, no organization picked or role refusal, **423** temporary lockout (5 wrong passwords -> 15 minutes, as the scenario files said), 429 code cooldown / daily limit. Four new shared error bases in `app/libs/common/errors.py`; a failure that must keep its counter raises a `FailureRecordedError` and the router commits first (`router.persist_recorded_failure`), because `get_db` rolls back on an exception.
- **WP2a, who may create organizations**: HEAD_ADMIN, CO_ADMIN and SALES of an internal organization (ACC-01 lists SALES; the brief said HEAD_ADMIN/CO_ADMIN); status changes stay HEAD_ADMIN / CO_ADMIN; `is_internal` true only by HEAD_ADMIN and only for a COMPANY.
- **WP2a, list parameters**: lists take `page` / `page_size` like every other domain, not the `offset` / `limit` the portal scenario sketched. Removing a member is `DELETE /memberships/{id}?reason=` (a query parameter, like the other delete endpoints).
- **WP2a, sign-up**: always an INDIVIDUAL personal organization (no `legal_form` in the body); legal texts are not accepted inside sign-up but afterwards through `POST /consents/` (`GET /legal-documents/pending` lists what is missing). Accepting is not enforced as a condition of use.
- **WP2a, invitations**: a new phone gets an INVITED user + INVITED membership + an SMS code (72 h) and accepts with `POST /auth/invitations/accept`; a phone that already has an active account gets only the INVITED membership and an SMS notice, and accepts with `POST /memberships/{id}/accept`. A FLEET_MANAGER may invite members who hold only the DRIVER role (ACC-10).
- **WP2a, organization picker**: login opens the only usable organization, else the remembered one (`user_state.last_organization_id`), else none; any endpoint that needs a `Principal` then answers 403 until `POST /auth/organization`. Session lifetime is 1 day when the person has an active membership in an internal organization, else 90 days (apps) or 7 days (browser).
- **WP2a, ACC-20 (ID-48)**: no DBML flag exists, so the sealed emergency HEAD_ADMIN is the account whose phone is `IDENTITY_EMERGENCY_ADMIN_PHONE`; its login alerts the other head administrators by (fake) SMS and a warning log, and is a normal `LOGIN_SUCCESS` audit row.
- **WP2a, role rules (ID-49)**: ORG_ADMIN only by organization creation or handover; HEAD_ADMIN / CO_ADMIN only by a HEAD_ADMIN and only in internal organizations; the DRIVER role is not checked against a driver profile (identity may not call `drivers`); the handover accepts a reason but only logs it (no reason column on `user_role_assignments`), and a role revoke takes none.
- **WP2a, audit log readers**: HEAD_ADMIN / CO_ADMIN of an internal organization read every entry; an ORG_ADMIN reads only their organization; the range is limited to 366 days (`IDENTITY_AUDIT_LOG_MAX_RANGE_DAYS`). Other domains write `VIEW` / `EXPORT` rows through `identity.service.record_data_access`; nothing calls it yet (WP2b).
- **WP2a, import contract**: the identity public surface is `service`, `types`, `exceptions` and `dependencies` (the FastAPI authentication module); `tests/test_import_contracts_smoke.py` allows `dependencies` for every domain, `tests/test_db_session_scope_smoke.py` now scans every `*router*.py` module and every router in it.
- **WP2a, feature catalog**: the ACC-* backend statuses are left `todo` (CLAUDE.md: statuses stay `todo` until the backend sync).

- **WP2b supersedes** the chunk 1, 4, 5 and 6 assumptions above that name actors in bodies or query parameters (fleet `organization_id`, `granted_by`, `requested_by`, `driver_id`, notification `user_id`): the caller is the actor now (ID-50).
- **WP2b, one role table (ID-50)**: `FEATURE_ROLES` / `roles_for(...)` in `identity/types.py` holds the `users` list of every feature of the owning domains; HEAD_ADMIN, CO_ADMIN and ORG_ADMIN are added to every feature (internal staff have the whole role set, ID-44; an ORG_ADMIN manages everything of their own organization and the data scope limits the reach). `SYSTEM` / `EXTERNAL` are dropped.
- **WP2b, data scope in services and repositories**: services take `principal: Principal`; the repositories take `organization_id: UUID | None` (None = no restriction) and the service passes `principal.data_scope`. Cross-domain `resolve_*` functions stay unscoped (system callers); the HTTP-facing function checks the reference's `organization_id` itself. `list_active_member_vehicle_ids` got an optional `organization_id` for the same reason.
- **WP2b, create bodies**: `organization_id` is optional in the vehicle, device, fleet, location, scan and support create bodies; without it the caller's organization owns the record, internal staff may name another one (validated through `identity.service.resolve_organization_for_new_record`, which also answers 404 for an organization the caller cannot reach). The dead `Vehicle/Telematic/FleetOrganizationNotFoundError` and `SupportOrganizationRequiredError` classes were removed.
- **WP2b, removed actor fields**: `granted_by` / `revoked_by` / `requested_by` (stations), `started_by` and the scan's `organization_id` default, `driver_id` of check-in and check-out (optional now), and the `user_id` query parameters of the notification endpoints are gone; the notification list has `mine_only` instead.
- **WP2b, delete endpoints**: vehicles, devices, fleets and drivers take an optional `reason` query parameter that becomes the change / status reason; charging stations already had `status_reason`.
- **WP2b, DRIVER-only callers**: they act on their own profile, see only their own sessions, scans, notifications and support cases, and read live telemetry only of the truck they are checked in to (DR-11, DR-14, CE-19, NT-14, SP-09). Managers may check another driver of their organization in or out.
- **WP2b, read access to chargers**: *view* (details, status, search) adds public and granted locations to *manage* (owner organization, internal staff); the nearby search applies it in SQL (CS-28).
- **WP2b, audit rows**: VIEW rows for the latest position and the history of a truck, a driver profile, and a manager's driving-session list (`record_data_access` in the routers, because they need the request's IP and user agent).
- **WP2b, new cross-domain edges**: `telemetry -> drivers` (`is_membership_checked_in_to_vehicle`) and two more functions on the existing `support -> drivers` edge; the domain-boundaries rule was updated.
- **WP2b, test support**: `tests/principals.py` builds a `Principal` (a customer ORG_ADMIN by default, `build_internal_principal()` for staff); `tests/conftest.py` has a fixture that skips the organization lookup; the PostgreSQL tests insert a fixed actor user into every temporary database (history rows and `added_by` point at it).

- **WP3 supersedes** the chunk 2 assumptions that the installed battery's capacity "comes with WP3/WP4" (`telemetry` now applies it, VH-21) and that `batteries` / `warranties` hold models only (their services, repositories and routers exist now); chunk 2's "ownership transfer is WP3" is done.
- **WP3, transfer orchestration (VH-21)**: `vehicles` cannot call `fleet`, `drivers` or `batteries` (one-way edges, FL-01, VH-13), so the transfer endpoint lives in `app/api/vehicle_transfer.py` and calls each owner's public service in the request's one transaction. This is the closest option to VH-12 that keeps the edges; the module is listed in domain-boundaries.md. The charging-policy, subscription and VIN-credential parts of VH-12 have no tables (parked) and are not done; a T-Box keeps its owner.
- **WP3, who may write**: BAT-01 and VEH-02 are `offer: internal` and the warranty entry is the warranty team's work, so battery, battery model, transfer and warranty writes use `internal_only=True` (the ORG_ADMIN the role table adds to every feature cannot write them); reads follow the data scope. VEH-03 catalog writes were internal-only already. Battery model and vehicle model reads need only a sign-in (reference data).
- **WP3, pack capacity wiring**: the precedence of VH-16 is applied in `telemetry` (`_resolve_vehicle_reference_with_pack_capacity`), not in `vehicles`, because `batteries -> vehicles` is the only allowed direction. Other domains that read `VehicleReference.battery_capacity_kwh` (none today besides telemetry) would get the model figure.
- **WP3, warranty rules not in the DBML**: no overlap of two ACTIVE warranties of the same object and type (409, from the portal scenario's "overlapping term"); `ends_on` before `starts_on` is a 400; a VOIDED warranty cannot be edited, voided again or restored; `limits` readings must be 0 or more. A soft delete means "entered by mistake" (VOIDED + reason).
- **WP3, vehicle list filters**: `q` (plate or VIN fragment), `status`, `vehicle_model_id`, `organization_id`. The fleet filter of VEH-01 is not offered (`vehicles` cannot ask `fleet`); `GET /fleets/{id}/vehicles` already lists a fleet's trucks.
- **WP3, VEH-05 and VEH-06**: activation (computed from the fitted device and the data received, VH-06) is left to WP4; the fault code catalog has no table in the DBML and is skipped.
- **WP3, battery status**: the code uses ACTIVE / INACTIVE (DM-25, the DBML), not the older ACTIVE / MAINTENANCE / DECOMMISSIONED of VH-16; a pack that is INACTIVE cannot be fitted.

- **WP4 supersedes** the chunk 3 assumptions that the status topic is not ingested ("WP4 adds the consumer once the vendor confirms the format") and that the config push does not require a mounted device: `telematics/ingestion/` ingests the provisional format now (TX-13), and a single push to a device that is not mounted answers 409.
- **WP4, status-report process**: a second MQTT process (`make telematics-status-dev`, `MQTT_STATUS_CLIENT_ID`, `MQTT_STATUS_REPORT_TOPIC`, `TELEMATICS_STATUS_QUEUE_SIZE`) rather than a second subscription inside the telemetry consumer, so a bad status message or its queue can never stop telemetry; the cost is one more process to run. ## Next steps (debugging phase)

The ten biggest items of the Known issues table, most severe first. Security
gaps come first.

1. **One-time codes in the log.** The fake SMS provider writes the code to the log (`identity/providers.py`); never run it outside development, and add a real provider before any deployment.
2. **`IDENTITY_TOKEN_SECRET_KEY` has no default.** Empty means a random key per process, so tokens die at restart and break across workers; require a value outside development (fail at start-up).
3. **Webhook secret.** `/payments/vietqr/notifications` is protected by one shared secret only (no replay window, no IP allow-list); a forged call credits a wallet. Add both and verify the provider's signature when a real one is chosen.
4. **Fleet-limit gaps (FL-10).** The limit is not applied to the organization notification list, support cases, charging sessions, bills, batteries, warranties, detail-by-ID endpoints, the organization-wide device-health list and the single-device config push; ending or locking a membership leaves its assignments open.
5. **No HTTP-level tests.** `httpx` is not a dependency, so 401 / 403 / 404 behaviour, the scan / stop / webhook routes and the OpenAPI wiring are proven only through endpoint functions with fakes and a few PostgreSQL tests. Add the dependency (with approval) and a thin set of route tests.
6. **Simulator seed scripts broken.** `simulator/seed_*.py` post old API shapes without a login or `organization_id`; the 2.0.1 simulator sends no `idToken`; no tariff is seeded (scan answers `409 NO_TARIFF`). Fix them, then run `e2e-sim` end to end.
7. **VietQR layout unverified.** Only the CRC and TLV structure are tested; scan a generated code with a real banking app and fix the field layout (tag 38, purpose in 62/08, MCC).
8. **Delivery inside the producer's transaction.** Push and e-mail are sent before commit, so a rolled-back alert could already be out; add an after-commit outbox with NTF-07 (`deferred.md` 96, 100).
9. **Hook failure leaves a COMPLETED session with a QUOTED bill.** Nothing sweeps such bills and no staff action settles one; add a sweep or an endpoint around the idempotent `settle_session_bill`, and make sure every process that ends sessions registers the hooks.
10. **History trigger without an actor.** The OCPP gateway, the monitors and device-reported writes still record `Unspecified change` with a NULL actor (DM-29); give them a system reason and switch the trigger back to raising.

Also queued: the recycled-phone check and rate limits (`deferred.md` 99), refresh-token reuse detection, the permission-granting step replacing the copied role table (ID-44), and the unbatched list queries once a benchmark justifies batching.
