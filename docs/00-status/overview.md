# Repo Status

Short, domain-level summary of what's actually implemented right now. This is
the source of truth for **progress at a glance** — unlike most of
`docs/01-requirements/`, which describes intended features and can be revised
independently of what's actually built. The one exception is
[`feature-list.md`](../01-requirements/feature-list.md): each feature there
carries this repo's backend implementation status directly (per `F-XX` item,
not just per domain), and it is also kept current as progress source of
truth — update both together when a change shifts a domain's overall status.
For technical depth (components, diagram, database, infra), see
[architecture.md](./architecture.md).

## Domains

| Domain | Status |
|---|---|
| `vehicles` | CRUD and soft delete (list filterable by `status` and `activation_status`), plus an F-F2 device-activation state machine (`PENDING → DEVICE_ASSIGNED → ACTIVATED`) and `GET /vehicles/activation-summary` for the fleet-wide success rate. Also carries a nullable `battery_capacity_kwh` (F-A6/F-C6's kWh-conversion input). |
| `telematics` | Device CRUD, mapping devices to vehicles: a VIN that matches no live vehicle is rejected (404), an explicit `vehicle_vin: null` unassigns, and a soft-deleted device no longer blocks a replacement (partial unique index `uq_telematics_active_vehicle`). A device whose vehicle was soft-deleted is ignored by ingestion mapping and the monitor. Runs a periodic device-health monitor (`telematics/monitoring/`, this backend's first non-event-driven background process) that alerts once per silence episode when a device stops reporting telemetry (F-J1/F-J3, partial — see `future.md`); "last seen" is the newest backend `received_at`, so a device with a skewed clock can't fake silence. Every device response carries read-time health (`last_seen_at`, `is_online`, `is_silent` — the monitor's own rule, `monitoring/silence_rule.py` — and `last_signal_strength_dbm`). Pushes a telemetry publish-interval config over MQTT (`telematics/commands/`, this backend's only MQTT *publish* — F-J2, partial) to one device or to every current member of a fleet (`POST /telematics/fleets/{fleet_id}/config`, one `published`/`skipped`/`failed` result per vehicle). |
| `telemetry` | Ingests via MQTT with a versioned message schema (`schema_version`), one message per transaction (a malformed or non-UTF-8 payload is logged and dropped; the ingestion process exits non-zero if its consumer or worker stops on its own). F-A1: the **latest** record per vehicle with `received_at` and a read-time `is_online` (`TELEMETRY_ONLINE_THRESHOLD_SECONDS`); NF-01/NF-04/NF-06 hardening deferred (`future.md` item 36). F-A2 tiered battery alerts: SOC-threshold-crossing detection raises a notification carrying the nearest *available* station (≥1 `Available` connector) and its coordinates. F-A3: `soh_percent`/`cycle_count` ingested, a below-threshold `SOH_ALERT` (threshold is a setting), and a daily battery-health trend (`GET .../battery-health`). F-A4 anomaly detection: high battery temperature, sudden voltage drop and new device error codes raise `ANOMALY_ALERT`s; cell/module vs. motor fault classification and motor-temperature detection are deferred (`future.md` items 42, 45). F-A5: a bounded time-range **history** query, and fleet **geofence** entry/exit detection in ingestion (`geofencing.py`, one `GEOFENCE_ALERT` per area entered or left; geofences are owned by `fleet`); true trip segmentation is deferred (`future.md` item 46). F-A6/F-C6 (MVP/POC scope): `GET /telemetry/vehicles/{id}/operating-report` (optional `granularity=day|week|month` in `APP_REPORT_TIMEZONE`, `format=csv`) and `.../energy-usage` fold SOC drops/rises from the same telemetry history into consumed/charged energy, distance and cost (flat tariff setting) — `charging_sessions` has no vehicle linkage, so this is a telemetry-based proxy, not a station-metered figure (see `docs/02-planners/done/backend-operating-energy-reports.md`). Fleet views (F-E1/F-A6) live here too, through a one-directional `telemetry → fleet` edge: `GET /telemetry/fleets/{fleet_id}/vehicles/latest` (member positions + online flag) and `GET /telemetry/fleets/{fleet_id}/operating-report[?format=csv]` (per-vehicle rows + fleet totals). |
| `charging_stations` | Station → EVSE → Connector topology CRUD, a gateway for **OCPP 2.0.1 and OCPP 1.6J** (one adapter per negotiated subprotocol), station directory metadata (location, power rating, connector standard, operating hours, maintenance status, computed connector count, read-time `available_connector_count`), a nearest-*available*-station lookup (F-A2) and a nearby-station radius search with an `is_available_only` filter (F-D1), all using PostGIS. "Available" = not deleted, `OPERATIONAL`, ≥1 connector whose last status is `Available`; `is_online` is not required. The gateway stores every OCPP frame verbatim in an append-only raw log (which also stamps `last_seen_at`, so `is_online` works for both protocols) and handles `StatusNotification` (F-C2): a connector's live status is kept exactly as reported (2.0.1's five values plus 1.6J's `Preparing`/`Charging`/`SuspendedEV`/`SuspendedEVSE`/`Finishing`, with `errorCode`/`vendorErrorCode`), 1.6J connector `0` (the whole charger) is stored on the station, and `GET /charging-stations/{id}/connectors` returns the charger and every gun in one read. Both protocols answer `BootNotification`/`Heartbeat` and record the charger's device info (vendor, model, serial, firmware); for 1.6J the gateway also captures the charger's configuration (`GetConfiguration`, incl. `SupportedFeatureProfiles`) after every boot (`GET /charging-stations/{id}/configuration`). Serves the all-stations energy ranking (`GET /charging-sessions/stations/energy`, F-C5) because it owns the station directory. 1.6J is verified against a simulator only — the real Willdigits charger has not been connected yet (`docs/02-planners/backend-ocpp16-charger-integration.md`). Assumes pre-provisioned topology; no reconnect/offline recovery, stale-status handling, fault alerting, remote commands or TLS/authentication yet (`future.md` items 27, 73-76). |
| `charging_sessions` | Session lifecycle for both protocols: 2.0.1 `Started → Updated/MeterValues → Ended`, and 1.6J `Authorize`/`StartTransaction`/`StopTransaction`/`MeterValues` (the backend assigns the integer `transactionId` from a database sequence; `idTag` stored, every tag accepted; stop reason and the charger's authoritative `meterStop` stored; the session is found by `(station, transactionId)`). All measurements live in one `charging_session_measurements` hypertable — the energy register drives the session total, other measurands (`SoC`, power, voltage, current, temperature, `Power.Offered`, vendor-specific) are stored as sent and readable via `GET /charging-sessions/{id}/measurements`. The session detail adds read-time `duration_seconds`, `soc_start_percent`, `soc_end_percent` and `max_power_kw`; the list filters by station, connector, status and start window. Still no retry, out-of-order recovery, DLQ, or dedup (`future.md` item 27); F-B2's four scoped correctness fixes still apply (per-event `seqNo`, a `COMPLETED` session refuses events, stale `MeterValues` can't overwrite a newer reading, unit-aware energy normalization). F-C5: a station-level energy total over a window and an hourly/daily energy series (`.../energy/series`, register deltas bucketed in `APP_REPORT_TIMEZONE`). |
| `notifications` | Generic backend-storage notification table (F-A2's delivery leg, also reused by F-A3/F-A4/F-A5/F-I2/F-J1/F-J3), polled via `GET /api/v1/notifications?after_id=` (`limit` bounded 1..`API_MAX_PAGE_SIZE` like every list endpoint), filterable by `vehicle_id`, `notification_type` and `severity`, with `order=desc` for the newest first; plus `GET /notifications/{id}`, `GET /notifications/unread-count`, `POST /notifications/mark-all-read` and per-notification mark-read. A JSONB payload carries type-specific fields so alert types (`BATTERY_ALERT`, `ANOMALY_ALERT`, `SOH_ALERT`, `DEVICE_OFFLINE_ALERT`, `SOS_ALERT`, `GEOFENCE_ALERT`, and future F-B5 types) share one table without a new endpoint per type. No push, no recipient scoping (no `identity` domain yet) — poll-only for now. |
| `drivers` | This backend's first brand-new domain since the initial baseline. Driver profile CRUD (list searchable by `q` — name, phone or license number — and filterable by the currently assigned `vehicle_vin`) plus a `driver_vehicle_assignments` **assignment-history table** (`assigned_at`/`unassigned_at`, this backend's first use of a partial unique index to enforce "one active vehicle per driver, one active driver per vehicle"), with smooth reassignment (auto-closes the driver's previous active assignment) and full per-driver assignment history (F-E4, done at MVP/POC scope). F-A9 (empty-trip detection) was considered alongside it but is suspended — no trip concept, driver auth, or consumption-curve data exists anywhere in this backend yet (`future.md` item 67). |
| `support` | Support case tickets (F-I1) and SOS intake (F-I2), done at MVP/POC scope. One `support_cases` table discriminated by `case_type` (`TICKET`/`SOS`) rather than two tables, since the spec ties them into one lifecycle. A response-SLA deadline (60 min for a ticket, ≤5 min for an SOS) is copied onto each row at creation time so a later config change never rewrites a past case's SLA; `is_sla_breached` is computed on read, not stored, against the first response time (never moved by later status changes), or `closed_at` for a case cancelled before any response, or else now. An SOS takes a `channel` (hotline fallback; coordinates required only for `IN_APP`) and raises a `CRITICAL` `SOS_ALERT` notification in the same transaction. The case list filters by status, type, vehicle, category, channel, driver, `awaiting_response` and `sla_breached`. Vehicle/driver context is client-supplied and validated against `vehicles`/`drivers`, not fetched from `telemetry`. A CLOSED/CANCELLED case refuses further updates. F-I4 (partner directory + dispatch routing) and F-I3 (maintenance booking) are deferred — see `future.md` items 68-69. |
| `fleet` | Fleet CRUD and vehicle membership (F-E1), done at MVP/POC scope — this backend's second brand-new domain. A `fleet_vehicle_memberships` **assignment-history table** mirrors `driver_vehicle_assignments`'s shape (`joined_at`/`left_at`, a partial unique index on `vehicle_id`), with one structural difference: no equivalent index on `fleet_id`, since a fleet legitimately holds many vehicles. Replaces the dead `vehicles.fleet_id` column (dropped entirely, not converted — `future.md` item 10, superseded). Vehicles are added and removed by VIN (`POST /fleets/{id}/vehicles` with the VIN in the body, `DELETE /fleets/{id}/vehicles/{vin}`); a member whose vehicle was soft-deleted stays in the fleet's vehicle list with `vin`/`license_plate`/`status` = null and is closed by membership ID (`DELETE /fleets/{id}/memberships/{membership_id}`). `GET /fleets` filters by `q` and `vehicle_vin`; the fleet's vehicle list by `status` and `q`. Owns **geofences** (`geofences` table, `/fleets/{id}/geofences` CRUD, GeoJSON polygon stored as `geography(POLYGON, 4326)`) and exposes `list_active_member_vehicle_ids`, `find_current_fleet_id_by_vehicle` and `list_geofences_containing` (`ST_Covers`) to `telemetry` and `telematics`. Live positions/online status and the fleet operating rollup are served by `telemetry` (`/telemetry/fleets/{fleet_id}/...`). F-E2 (KPI dashboard) is deferred — see `future.md` item 72; F-E3/F-A8 remain hard-blocked on `charging_sessions` having no vehicle/driver linkage. |

## Cross-cutting backend structure

- **Errors:** every domain exception inherits one shared base in
  `app/libs/common/errors.py` (`NotFoundError` 404, `ConflictError` 409,
  `InvalidInputError` 400, `UpstreamUnavailableError` 502), mapped once by
  the handlers in `app/api/main.py` (`{"detail": ...}` body); routers no
  longer wrap service calls in `try/except`.
- **Shared helpers:** `libs/common/clock.utc_now`,
  `libs/common/pagination.normalize_page_window` (every paginated list; a
  `page_size` below the default is honoured) and `libs/db/enums.enum_values`.
- **Boundaries:** import-linter lets a domain import only another domain's
  `service`, `types` and `exceptions` modules; larger domains keep internal
  modules behind their public `service.py` (`telemetry`'s
  `time_windows`/`mappers`/`reports`/`detection`/`alerting`/`geofencing`,
  `charging_stations`' `ocpp_state_service`/`ocpp_state_repository`);
  `tests/test_import_contracts_smoke.py` fails when a domain module other
  than `service`/`types`/`exceptions` is missing from its contract.
  `make lint` type-checks both `app` and `tests`.

## Database

Single baseline migration: `0001_baseline_schema` (edited in place during the
bootstrap phase; `make db-reset` rebuilds the database from it).

## Not built yet

Web portal, vehicle app, identity/RBAC, policy, billing/payment, trip
segmentation and push/multi-channel delivery have no active source in the
repo. `notifications` has a backend-storage/polling slice but not the
multi-channel delivery F-F3 describes. `drivers` has a CRUD/assignment
slice (F-E4), but F-A9 (empty-trip detection) remains unimplemented,
blocked on a trip concept this backend doesn't have yet. `support` has a
ticket/SOS-intake slice (F-I1/F-I2), but F-I4's partner directory/dispatch,
F-I3's booking and an SLA-breach monitor remain unimplemented. `fleet` has
a CRUD/membership/geofence slice (F-E1, F-A5) and a fleet operating rollup
exists in `telemetry`, but F-E2's KPI dashboard, F-E3's charging & warranty
report, and F-A8's per-driver efficiency report remain unimplemented — the
latter two are hard-blocked on `charging_sessions` having no vehicle/driver
linkage. Geofences are scoped to a fleet until customer accounts exist
(`future.md` item 86). See
[`docs/01-requirements/future.md`](../01-requirements/future.md) for the
full list of deferred components and why.
