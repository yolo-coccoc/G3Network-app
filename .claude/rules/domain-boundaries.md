# Domain boundary rules (backend)

> Read this file before adding a new domain, calling across two domains, or
> when unsure whether an import violates a bounded context. Directory
> structure in [directory-structure.md](./directory-structure.md). Which
> product features a domain (existing or future) serves is mapped in
> [`docs/01-requirements/feature-list.md`](../../docs/01-requirements/feature-list.md)
> (each feature carries a **Backend domain:** field).

- Each directory under `backend/app/domains/` is **1 bounded context**. A domain may only call another domain through that domain's **public `service.py`** — **never** import/query `repository.py`/`models.py` of another domain directly.
  - This rule only applies **between different domains**. Calling directly between files **within the same domain** is fine (e.g. `telemetry/ingestion/mqtt_consumer.py` calling `telemetry/repository.py` directly — both are inside the `telemetry` domain, so this doesn't violate the rule).
- **`telemetry`** is the real-time and historical vehicle data domain: other domains may depend on its public service once future query APIs are finalized. The ingestion flow receives `telematic_serial` and calls the `telematics` domain's public service to resolve `(telematic_id, vehicle_id)`; it never imports `telematics.models`/`repository` directly. The `telematics` domain is allowed to call the `vehicles` public service to resolve and validate vehicle mapping. `telemetry`'s F-A6/F-C6 reports reuse this same existing `telemetry → vehicles` edge (via `resolve_vehicle_reference_by_id`) to read battery capacity alongside the existing vehicle-existence check — no new edge, just a wider `VehicleReference` DTO.
- **`telematics`'s F-J2 config-push publisher** (`telematics/commands/`) calls no other domain's service — it only reads its own `telematics` repository and publishes over MQTT directly, so it introduces no new domain-boundary edge.
  - **`telematics ↔ telemetry` is bidirectional** (noted explicitly since every other domain pair here is one-directional): `telemetry → telematics` for serial resolution during ingestion (above), and `telematics → telemetry` for F-J1/F-J3's periodic device-health monitor (`telematics/monitoring/`), which calls `telemetry.resolve_last_telemetry_at(db, vehicle_id)` to check a vehicle's last-seen time. Both directions only call the other domain's public `service.py`, never its `repository`/`models`. When `import-linter` (bullet below) is added, this pair needs an explicit allowed-cycle exception rather than being treated as a boundary violation.
- **`notifications`** (F-A2) is a leaf domain: it stores/reads notifications and depends on no other domain. `telemetry`'s ingestion path calls `notifications`' public service to raise a battery-threshold (F-A2), anomaly (F-A4), or SOH (F-A3) alert, and separately calls `charging_stations`' public service to resolve the nearest operational station for the F-A2 alert's payload — all one-directional (`telemetry → notifications`, `telemetry → charging_stations`), neither domain calls back into `telemetry`. `telematics`' device-health monitor (F-J1/F-J3) also calls `notifications`' public service the same one-directional way.
- **`charging_stations`** owns Charging Station/EVSE/Connector topology and OCPP 2.0.1. **`charging_sessions`** only receives normalized data from OCPP to store events, meter data, and session lifecycle; it doesn't own a WebSocket/OCPP adapter and never calls back into `charging_stations`. The OCPP adapter calls the `charging_sessions` public service, keeping the dependency one-directional: `charging_stations → charging_sessions`. Technical status history, authorization, RFID/driver/vehicle policy, remote-control business logic, pricing, payment, and debt are out of MVP scope and must be recorded in `docs/01-requirements/future.md` before being reopened.
  - **The OCPP 1.6J work added no new domain edge.** The OCPP adapters (both protocols) still only call `charging_sessions`' public `service.py`, and `charging_sessions` still never calls back. Its public surface grew: `allocate_ocpp16_transaction_id`, `has_active_session_on_connector`, `resolve_session_by_transaction` (returns the frozen `TransactionSessionReference`), `ingest_measurements`, and new optional keyword-only arguments on `ingest_transaction_event`/`MeterSampleInput` (`id_tag`, `stop_reason`, `meter_stop_wh`, `context`) — every one takes and returns primitives/frozen dataclasses, never an ORM model. Inside `charging_stations`, the OCPP adapters may call the domain's own `repository`/`service` directly (same domain).
- **`drivers`** (F-E4) owns driver profiles and vehicle-assignment history (`driver_vehicle_assignments`, an open/close assignment-history table, not a single current-vehicle column). It depends one-directionally on `vehicles`' public service (`resolve_vehicle_reference_by_vin`/`resolve_vehicle_reference_by_id`) to resolve and validate a VIN on assign, and to enrich responses/history rows — the same shape as the existing `telematics → vehicles` edge. `vehicles` never calls back into `drivers`. F-A9 (empty-trip detection) would also touch this domain but is suspended (no trip concept exists in this backend yet) — see `docs/01-requirements/future.md`.
- **`support`** (F-I1 tickets, F-I2 SOS) owns `support_cases`, one table discriminated by `case_type` rather than two tables (the spec ties a ticket and an SOS into one lifecycle). It depends one-directionally on `vehicles`' public service (`resolve_vehicle_reference_by_vin`) to resolve/validate a VIN and on `drivers`' public service (`resolve_driver_reference_by_id`) to validate a driver ID and enrich a case's `driver_name` — the same one-directional edge shape as `telematics → vehicles`. Neither `vehicles` nor `drivers` calls back into `support`. Deliberately **not** wired to `telemetry` — vehicle context (VIN/location/error code) is client-supplied at case-creation time, not fetched live, so `support` has no `telemetry` edge at all. F-I4 (partner directory/dispatch routing) would extend this domain but is deferred — see `docs/01-requirements/future.md`.
- **`fleet`** (F-E1) owns fleet records and vehicle-membership history (`fleet_vehicle_memberships`, the same open/close history-table shape as `driver_vehicle_assignments`, with one structural difference: only `vehicle_id` gets a partial unique index, since a fleet legitimately holds many vehicles at once). It depends one-directionally on `vehicles`' public service (`resolve_vehicle_reference_by_vin` to resolve/validate a VIN on membership add, `resolve_vehicle_summary_by_id` — a new sibling DTO to `VehicleReference` — to enrich F-E1's vehicle list) — the same one-directional edge shape as `telematics → vehicles`/`drivers → vehicles`. `vehicles` never calls back into `fleet`. This edge **replaced** the dead `vehicles.fleet_id` column (a `String(36)` with no FK, dropped entirely rather than converted — see `docs/01-requirements/future.md` item 10). F-E2 (KPI dashboard) would extend this domain but is deferred — see `docs/01-requirements/future.md`.
- Once the `identity` domain (auth & RBAC) is added to the repo, it becomes the foundational domain: every other domain is allowed to depend on it (via `service.py`), while it depends on none of them. This domain has no active source yet — don't create a placeholder for it before a concrete task exists.
- Detailed dependency directions between specific individual features **are not repeated here** — they're already fully covered in the "Dependencies" column of `docs/01-requirements/feature-list.md`; this document only states the general principle at the domain level.
- A newly added domain must reference the correct feature code in `docs/01-requirements/feature-list.md` (e.g. `F-C1`, `F-B2`).
- Once the CI/CD platform is finalized, add **`import-linter`** to block domain A from directly importing domain B's internals (`repository`/`models`). This package/config isn't installed yet, so reviewing and searching for imports manually is mandatory.
